# T4 — HTTP API

## Prompts that mattered
- "Use the installed library versions (check node_modules .d.ts files)" → read `fastify-type-provider-zod@7.0.0`'s
  `.d.ts`: v7 serializes responses with Zod's `safeEncode`, so the response schemas really are enforced, and it exports
  `hasZodFastifySchemaValidationErrors` for the error handler and `FastifyPluginAsyncZod` for a typed route plugin.
- "Tie the response schemas to the domain types so they cannot drift" → `feedbackViewSchema`, `analysisAttemptSchema`
  and `feedbackDetailSchema` end with `satisfies z.ZodType<…>`. `satisfies` (not a `: z.ZodType<…>` annotation) keeps
  the object type, so `feedbackDetailSchema` can `.extend()` the view schema; dropping a field is a compile error.

## Where the AI was wrong / low quality and how it was corrected
- First draft of `createSubmitFeedbackBodySchema` had no return type (inferred) → CLAUDE.md requires explicit return
  types on exported functions → annotated `z.ZodObject<{ content: z.ZodString }>` (`.trim().min().max()` stay `ZodString`).
- I assumed rethrowing from `setErrorHandler` hands non-validation errors to Fastify's default handler, then checked it
  with a throwaway script (not committed): a repository throw gives the default 500 body; malformed JSON gives 400.

## Shortcuts / tradeoffs taken
- Not covered by the brief: `maxContentLength` is a runtime setting, so the body schema is a factory,
  `createSubmitFeedbackBodySchema(maxContentLength)`. It is still pure Zod, so a UI can import it with its own limit.
- Not covered by the brief: the `:id` param is `z.string().min(1)`, not `z.uuid()`, so an unknown or malformed id
  gets the 404 the brief asks for rather than a 400.
- Not covered by the brief: one `submitFeedbackResponseSchema` (`duplicate: boolean`) serves both 202 and 200.
- Malformed JSON bodies are a Fastify 400 error, not a Zod one. They go to the default handler and the route's 400
  schema strips the body to `{ error: 'Bad Request' }`: matches the contract, but the parse reason is lost. Not
  changed because the brief only specifies Zod validation errors.
- The 409 body reports the status read by `findById` just before the failed `transition`. Under a race it can be a
  moment stale; it is informational only and the transition itself is still atomic.
- `buildApp` uses `logger: true` as the brief says, so `npm test` prints Fastify's JSON request logs. The `buildApp`
  contract has no logger option, so I did not silence it in tests.
- No 500 response schema: unexpected errors use Fastify's default error body.

## Walkthrough for the owner
- `src/api/feedback.schemas.ts` — every request and response Zod schema, plus inferred types. Worth knowing: it imports
  only `zod`, `analysisResultSchema` and `FEEDBACK_STATUSES`, so a UI can import it; the `satisfies z.ZodType<FeedbackView>`
  lines are what make a drift between API and domain types a compile error.
- `src/api/feedback.routes.ts` — a Fastify plugin with the four routes. Each declares body/query/params and one response
  schema per status code; handlers only call the repository and `enqueue`. Retry relies on `transition(FAILED → RECEIVED)`
  returning false for the 409, so two retry clicks cannot both enqueue.
- `src/api/app.ts` — `buildApp(deps)`: Fastify with logger, the Zod validator and serializer compilers, an error handler
  that turns Zod validation errors into `400 { error }`, and the routes plugin.
- How to see it work: `npm test -- test/api` (21 tests with `app.inject()` on an in-memory DB, `enqueue = vi.fn()`).
