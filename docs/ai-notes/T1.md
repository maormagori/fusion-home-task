# T1 — Scaffold + contracts

## Prompts that mattered
- "Install the latest stable versions; use context7 docs for Drizzle (sqlite + better-sqlite3 + migrator), Zod v4 and
  drizzle-kit config rather than guessing APIs" → context7 returned Drizzle **v1 beta** docs (`migrate(db)` with no
  options, folder-per-migration layout). The installed `drizzle-orm@0.45` wants `migrate(db, { migrationsFolder })`.
  I checked the installed `.d.ts` files and used those signatures instead.
- "status with a CHECK constraint on the 4 values" → built the CHECK SQL from `FEEDBACK_STATUSES`, so the DB constraint,
  the Drizzle column `enum` and the TS type all come from one list.

## Where the AI was wrong / low quality and how it was corrected
- First DB test expected the thrown message to contain `CHECK constraint failed` → Drizzle 0.45 wraps driver errors
  in a `DrizzleQueryError` whose message is just "Failed to run the query …"; the SQLite error is on `.cause` →
  the test now asserts `cause.code === 'SQLITE_CONSTRAINT_CHECK'`. **T2 note:** catch/inspect `error.cause`, not `error.message`.
- `npm install @types/node` pulled v26 while we run Node 24 → pinned `@types/node@24` so types match the runtime.

## Shortcuts / tradeoffs taken
- `MIGRATIONS_FOLDER = './drizzle'` is relative to the **working directory**, not the source file. All scripts and CI
  run from the repo root, and with `rootDir: "."` the compiled file lives at `dist/src/db/`, so a module-relative path
  would differ between `tsx` and `dist`. Running from another directory would fail to find migrations.
- `npm audit` reports 4 moderate advisories, all from `esbuild` inside `drizzle-kit`'s dev-only dependency chain
  (`@esbuild-kit/*`). They do not ship at runtime; `npm audit fix --force` would downgrade drizzle-kit, so left as is.
- Latest stable versions turned out to be TypeScript 7 (native compiler), Vitest 5, Zod 4.6, openai 7. Typecheck and
  build both work with TS 7 and need no extra config.
- `npm run test:llm` uses a second config, `vitest.llm.config.ts`, with a 120s test timeout. Until T3 adds an
  `*.llm.test.ts` it exits with "No test files found"; I did not add `passWithNoTests`.
- `config.ts` uses `z.object` (not strict) because `process.env` holds many unrelated variables; unknown keys are dropped.
- `tsconfig` `include` also covers `*.config.ts` so the vitest/drizzle configs are type-checked too.

## Walkthrough for the owner
- `src/config.ts` — one Zod schema over env vars with the §7 defaults; `loadConfig(env)` parses it. Numbers use
  `z.coerce.number()` because env values are always strings; a bad value throws a ZodError naming the variable.
- `src/domain/types.ts` — the shared interfaces from CLAUDE.md, copied exactly. `FEEDBACK_STATUSES` is the single source
  for status values.
- `src/analysis/analysis.schema.ts` — the strict Zod schema the LLM output must pass; `strictObject` is what rejects extra keys.
- `src/db/schema.ts` — Drizzle tables. Worth knowing: the unique index on `content_hash` is what makes dedup safe, the
  unique `(feedback_id, attempt_number)` stops two attempts getting the same number, and the CHECK comes from `FEEDBACK_STATUSES`.
- `src/db/database.ts` — `openDatabase(path)` creates the parent dir, opens SQLite with WAL + foreign keys, runs
  migrations synchronously, and returns the Drizzle instance. `:memory:` gives each test a fresh, migrated DB.
- `drizzle/0000_*.sql` — generated by `npm run db:generate`; never edit by hand, change `schema.ts` and regenerate.
- `.github/workflows/ci.yml` — `npm ci` → typecheck → `npm test` on Node 24 for every PR.
- How to see it work: `npm install && npm run typecheck && npm test` (12 tests in `test/config.test.ts`,
  `test/db/database.test.ts`, `test/analysis/analysis.schema.test.ts`).
