# T2 — Feedback repository

## Prompts that mattered
- The T2 brief ("single `UPDATE … WHERE id = ? AND status = ?`, returns `changes === 1`", "avoid N+1 in `list`") →
  `transition()` became one conditional UPDATE, and `list` became one query: feedback LEFT JOIN a grouped subquery over
  `analysis_attempts` (`count()` + `max(result_json)`).
- "Use the installed library versions; check node_modules .d.ts files" → I checked `drizzle-orm@0.45` typings for the
  sync better-sqlite3 API: `.run()` returns `{ changes }`, `.get()` / `.all()` are sync, and `db.transaction(cb)`
  returns the callback's value synchronously, so `recordAttempt` can return the row straight from the transaction.

## Where the AI was wrong / low quality and how it was corrected
- First plan for `list` was a page query, then a second query per item for attempts → that is the N+1 the brief
  forbids → replaced by the grouped subquery joined once.
- First draft of `transition` built the SET object with a conditional spread (`...(x !== undefined && {...})`) →
  correct but takes a second read → a plain `updates` object plus an `if`, per the "boring version" rule.

## Shortcuts / tradeoffs taken
- `analysis` comes from `MAX(result_json)` per feedback. This relies on the rule that a run ends on its first valid
  result. A manual retry only leaves FAILED, and a FAILED run has no valid result, so in practice there is at most one
  non-null `result_json`. If that rule ever changes, MAX would pick by text order, not the latest attempt. Commented in code.
- Not covered by the brief: ordering ties. `created_at` has millisecond precision and repeats in fast inserts
  (tests do this), so `list` and `listIdsByStatus` break ties with SQLite's implicit `rowid` (insertion order).
- Not covered by the brief: `insertOrGetExisting` throws `Feedback with content hash … not found after insert` if the
  select after the insert finds nothing. This cannot happen (the row was just inserted or already existed) but the
  `.get()` result is typed as possibly undefined, and throwing reads better than a `!` assertion (forbidden).
- `recordAttempt` reads `MAX(attempt_number)` and inserts in one transaction. better-sqlite3 is sync on one connection,
  so this cannot interleave anyway; the transaction also covers the `updated_at` bump and keeps the two writes atomic.
  The unique `(feedback_id, attempt_number)` index from T1 is the last line of defense.
- `result_json` is read back with `JSON.parse(...) as AnalysisResult` (cast at a parsing boundary, commented), not
  re-validated with Zod: it was validated before it was written.
- `feedback.repository.ts` is ~200 lines, over the ~150 guide. It is one interface, one factory with eight methods, and
  three row mappers; splitting it would scatter one responsibility across files.
- One test calls `transition(DONE → RECEIVED)`, which the state rules forbid, to check that `analysis` is hidden
  for a non-DONE item that has a result. `transition` intentionally does not validate transitions (brief).

## Walkthrough for the owner
- `src/feedback/content-hash.ts` — `normalizeContent` (trim, collapse whitespace, lowercase) and `hashContent`
  (SHA-256 hex of the normalized text). The hash is what the unique index dedups on; the stored content is the original.
- `src/feedback/feedback.repository.ts` — the only code that touches the DB. Worth knowing:
  - `insertOrGetExisting`: `INSERT … ON CONFLICT (content_hash) DO NOTHING`, then select by hash; `created` is
    `changes === 1`, so two concurrent identical submits get the same row and only one sees `created: true`.
  - `transition`: `UPDATE … WHERE id = ? AND status = ?`. Returning `false` when no row matched is what makes the
    worker's `RECEIVED → ANALYZING` claim atomic. `lastError` is only written when the key is passed (`null` clears it).
  - `selectViews` is shared by `list` and `getDetail`, so `attemptCount` and `analysis` are computed the same way in both.
  - `toFeedback` / `toAttempt` map DB rows to domain types; `toAttempt` parses `result_json`.
- How to see it work: `npm test -- test/feedback` (4 content-hash tests, 17 repository tests on an in-memory DB with the
  real migrations).
