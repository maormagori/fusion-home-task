## Shortcuts / tradeoffs taken
- Not covered by the brief: after a successful claim, `processFeedback` throws `Feedback <id> not found after it was
  claimed` if `findById` returns null. It cannot happen (the claim just updated that row), but the type is nullable and
  `!` is forbidden; same reasoning as T2's `insertOrGetExisting`. The queue's job wrapper logs it.
- Not covered by the brief: the return values of the final `ANALYZING → DONE/FAILED` transitions are ignored. The
  worker owns the item while it is ANALYZING (only startup recovery moves it back, and that runs before any job), so
  they cannot lose.
- `latestError` starts as `''` and is always overwritten, because `MAX_ATTEMPTS` is validated as positive in `config.ts`.
- No graceful shutdown (SIGTERM → close server, wait for `queue.onIdle()`). Not in the brief; if the process stops
  mid-analysis, startup recovery puts the item back to RECEIVED, so no work is lost, only repeated.
- `enqueue: queue.enqueue` passes the method by reference. It is safe because the queue is a closure, not a class
  (no `this`).

## Walkthrough for the owner
- `src/queue/analysis-queue.ts` — a thin wrapper over `p-queue`. Worth knowing: the concurrency limit lives only here,
  and `runJob` turns a throwing job into a log line, because nobody awaits a queued job.
- `src/queue/analysis-worker.ts` — `processFeedback`, the retry + correction loop from ARCHITECTURE.md §5.2. Worth
  knowing: it does nothing unless it wins the conditional `RECEIVED → ANALYZING` claim; every LLM call gets exactly one
  attempt row; `invalid_output` appends `[assistant: raw, user: errors]` so the model can correct itself, while
  `llm_error` resends the same messages (the SDK already did transport backoff).
- `src/server.ts` — wiring: config → DB → repo → LLM client → queue → startup recovery (`ANALYZING → RECEIVED`, then
  enqueue every RECEIVED id) → `buildApp` → `listen`. It is the only file with module-level instances.
- How to see it work:
  - `npm test -- test/queue` (queue concurrency + throwing job; worker skips a non-RECEIVED item; worker ends FAILED
    after 3 attempts against an unreachable LLM).
  - `npm run test:llm` (worker takes a real item to DONE with one valid attempt).
  - Recovery: create a DB with one RECEIVED and one ANALYZING item, then `DB_PATH=<that db> npm run dev`. The log
    shows `"interruptedCount":1,"enqueuedCount":2` and both items reach DONE.

### Shortcuts / tradeoffs taken
- The "unexpected error" test wraps the real repository with `{ ...repo, recordAttempt: () => { throw … } }`.
  It is not a fake LLM (the LLM client is the real one, pointed at the unreachable port); it is the simplest way to
  make code inside the claimed section throw.
- Logged fields: `feedbackId`, `attemptNumber`, `kind`, `error` / `lastError`, counts. Never content or raw responses.
  Validation errors can include a short excerpt from `JSON.parse` ("Unexpected token … is not valid JSON"); accepted.
- The warn line is skipped on the last attempt; the FAILED info line right after it carries the same error.
- Test files still use status string literals: they assert the wire/DB values, so a literal is the point there.
- The recovery log line now comes before the enqueue loop: p-queue starts jobs synchronously on `add`, so logging after
  the loop printed "claimed" lines before the recovery summary.
